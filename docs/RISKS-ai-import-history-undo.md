# RISKS — AI 임포트 처리 내역 & 개별 되돌리기

| # | 리스크 | 영향 | 완화책 |
|---|---|---|---|
| R1 | 되돌리기로 실제 결제 데이터 삭제(비가역) | 높음 | 삭제 전 확인 모달 · 되돌리기도 event_log로 추적 · 배치/개별 명확 구분 |
| R2 | 신규 등록 삭제가 다른 결제까지 영향 | 높음 | 그 enrollment에 다른 payment_record가 있으면 등록 유지, 기록만 삭제(planUndo에서 판정) |
| R3 | 되돌리기 부분 실패로 상태 불일치 | 중간 | 건별 성공/실패 집계, 성공분만 '취소됨' 처리, 잔액 재동기화는 성공 건만 |
| R4 | savedItems ID 유실(저장은 됐는데 화면 전달 실패) | 중간 | 로그(event_logs)에 batchId로 남아있어 로그 화면에서 사후 추적/수동 정리 가능 |
| R5 | 타 조직 기록 되돌리기 시도(주입) | 높음 | undoImport에 RLS org 가드(기존 confirm 패턴 재사용) |
| R6 | 헤드리스로 최종 검증 불가 | 중간 | 순수 로직 단위테스트로 최대 커버 + 실기기 E2E를 완료 조건으로 |
| R7 | 동시 편집(다른 화면에서 같은 enrollment 수정 중 되돌리기) | 낮음 | 되돌리기 후 재동기화가 SUM 기준이라 자가 치유 · 버튼 busy 처리 |

## 롤백 전략
- 기능 자체가 플래그 없이도 안전(표시/로그는 부가적, 되돌리기는 사용자 명시 동작).
- 문제 시 P3/P4(되돌리기)만 UI에서 숨기고 P1/P2(로그·표시)는 유지 가능.
